# CareMate 现场交接：视觉、手机摄像头与 Debug

> 用途：到开发现场后，按这份文档分工和验收。它面向不熟悉硬件的视觉/软件同学，也可以直接转发给硬件队友。
>
> 当前基线：仓库 `main` 分支提交 `e8b2549`，全量回归 27 套、367 条通过。现场唯一执行端是仓库里的 `code/hand_controller/arm_service.py`，不要启动 `caremate_d_kit` 中的同名服务。

## 1. 先记住三条边界

1. 手机视觉模块只负责“看见”和“上报”：从手机取 JPEG 帧、计算变化能量、判断疑似跌倒，然后只向主脑发送 `POST /mock/fall`。它不直接调用 `arm_service`，也不直接发机械手动作。
2. 真实 RH56F2、24V 电源、串口、寄存器和 Panthera SDK 由硬件队友负责。你可以协助记录现象、日志和接口响应，但不要凭猜测改寄存器或接线。
3. 现场调试先走 mock 和只读检查；只有寄存器资料、手号、端口和电源都确认后，硬件队友才可以打开真实写入安全门。遇到不确定、异常响声、异常电流或动作失控，立即停止真实动作并恢复 mock。

## 2. 你负责的事情

### 2.1 手机摄像头接入

- 在手机上安装并配置 IP Webcam（或队友指定的 MJPEG/单帧 JPEG 应用）。
- 让手机和收流机器处于同一 Wi-Fi 或热点，记下手机地址，例如 `http://192.168.1.23:8080`。
- 将手机固定在支架上，镜头朝跌倒区域，俯角约 30°、距离约 2–3 米；画面必须同时覆盖老人活动区和地面。
- 负责确认浏览器能打开手机控制页、`/shot.jpg` 能返回图片，并记录手机 IP、网络名称和摆放位置。

### 2.2 视觉算法现场标定

仓库脚本是 `code/camera/phone_fall_watch.py`。它将每帧缩放为 48×32 灰度图，计算相邻帧的变化能量和纵向重心。它是跌倒触发器，不保存视频帧，也不把画面发送到外网。

现场必须记录三组数：

| 场景 | 做法 | 记录内容 |
|---|---|---|
| 静止 | 画面静止 10 秒 | 能量 `e` 的范围和平均值 |
| 正常活动 | 走动、摆手各 5 次 | 能量最高值 `b_max` |
| 模拟跌倒 | 缓慢、完整地倒地 3 次，倒地后保持静止 | 能量最低值 `c_min` |

阈值按下面的公式选，不要凭感觉乱改：

```text
thresh = b_max + (c_min - b_max) × 0.4
```

如果正常活动和模拟跌倒的能量区间没有间隔，先调整手机位置、光照和取景范围，再重新采样；不要只靠把阈值调得很低来“解决”。

### 2.3 主脑接口和端到端 Debug

- 确认主脑地址和端口，例如 `http://127.0.0.1:8000` 或 X5 在局域网中的地址。
- 视觉模块只使用：

  ```text
  POST {master}/mock/fall?room=客厅&src=phone_watch
  ```

- 先用 `--arm 0` 观察数据，不触发主脑；完成阈值标定、主脑联通和下游准备后才切 `--arm 1`。
- 记录每次触发的时间、能量值、阈值、HTTP 状态码、主脑日志和最终联动到哪一步。
- 如果主脑收到了 200，但机械手没有动作，先把问题交给主脑/硬件链路排查，不要在手机脚本里直接补发机械手命令。

### 2.4 你可以做的 Debug

- 检查手机 IP、热点、收流 URL、主脑 URL、端口和防火墙。
- 用 `--arm 0` 判断是“手机没送到帧”“算法没触发”还是“主脑没收到事件”。
- 对照静止/摆手/跌倒三组数据调整 `--thresh`，一次只改一个参数。
- 收集日志、复现步骤、输入场景和预期/实际结果，提交代码前先在 mock 环境回归。
- 只修改手机视觉模块或主脑接口适配；不要修改 RH56 寄存器表、串口初始化或硬件动作映射。

## 3. 硬件队友负责的事情

### 3.1 真机前置确认

- 确认 24V 电源规格、急停/断电方式、接线状态和现场安全距离。
- 确认手 #1、手 #2 的实际从站 ID、串口或同一 RS485 总线关系。
- 根据官方 RH56F2 资料核对目标、速度、状态、控制四类寄存器和动作单位；禁止使用猜测地址。
- 在仓库内安装硬件依赖并运行预检，确认端口、权限、设备节点和读回路径。
- 确认 `caremate_d_kit` 里的 `arm_service.py` 不启动，所有动作请求都进入仓库版本。

### 3.2 真实动作链

只有下面三件事同时满足，才允许进入真实写入：

```text
MOCK_SERIAL=0
RH56_REGMAP_CONFIRMED=1
code/hand_controller/rh56_register_map.py 中 PROVISIONAL=False
```

硬件队友需要逐项记录：

- 端口/总线和手号是否对应；
- 低风险姿态 `fingers_5`、`release`、`thumbs_up` 是否正确；
- 手 #2 的 `gentle_hold`/`comfort_rhythm` 是否为同一个轻握节拍序列；
- `/status` 的读回状态是否稳定；
- 断电、急停和异常响应是否可用。

真实动作必须从单个低风险姿态开始，确认速度、方向和限位后再跑完整演示。Panthera SDK 未拿到时，硬件队友只能保留 SDK 插槽或让动作明确失败，不能伪造成功。

### 3.3 X5 和部署

- 在 X5 上确认 Python 依赖、服务启动方式、权限和自启动配置。
- 先在笔记本运行同一脚本，再搬到 X5；确认 X5 能访问手机 IP 和主脑端口。
- 若主脑与视觉脚本在同一块 X5 上，视觉脚本的 `--master` 使用 `http://127.0.0.1:8000`；如果脚本在笔记本上，则使用 X5 的局域网地址。
- 修改部署脚本后，重新执行离线 mock 回归；现场真实启动由硬件队友负责。

## 4. 到现场的执行顺序

### P0：先对齐，不接触真实动作

1. 你和硬件队友先确认负责人：谁维护主脑，谁维护手服务，谁记录现场数据，谁负责最终演示口令。
2. 确认当前代码版本是仓库 `main` 的最新提交；所有人从同一个仓库目录启动服务。
3. 写下三项地址：手机 IP、主脑地址/端口、收流机器或 X5 地址。确认它们是否在同一网络、是否能互相访问。
4. 先启动 mock 主脑和仓库内的 `arm_service`，用 `/status`、`/pose` 或演示脚本确认软件链路。

### P1：你先完成手机视觉闭环

1. 手机开流：640×480、画质约 70%、锁屏继续推流或保持前台，记录地址。
2. 浏览器打开手机控制页，确认能看到实时画面；再确认 `/shot.jpg` 可访问。
3. 安装 Pillow，在仓库根目录执行：

   ```powershell
   python -m pip install -r code/requirements-phonecam.txt
   python code/camera/phone_fall_watch.py `
     --phone http://<手机IP>:8080 `
     --master http://<主脑地址>:8000 `
     --arm 0
   ```

4. 完成静止、正常活动、模拟跌倒三组采样，算出阈值并写入现场记录。
5. 用 `--arm 0` 复测：静止不触发，挥手不应连续触发，模拟跌倒能打印 `[FALL]` 预警。
6. 对主脑做一次接口验证，确认 `POST /mock/fall` 返回 200，并在主脑日志中看到 `src=phone_watch`。

### P1：硬件队友并行做真机前置

硬件队友在你完成视觉标定的同时，负责电源、手号、端口、寄存器和 Panthera/X5 检查。你不要代替他猜测寄存器或接线。只要真实后端的任何一项未确认，继续使用 mock。

### P2：联合验收

1. 先由硬件队友完成单个低风险真实姿态和 `/status` 读回。
2. 你将视觉脚本切换为 `--arm 1`，先做一次受控模拟跌倒。
3. 逐层记录：手机检测 → 主脑收到 `/mock/fall` → 询问老人 → 超时升级 → 求助/通知 → 手 #2 轻握 → 家属端或大屏反馈。
4. 连续完成 3 次完整触发，记录误报、漏报和每一层的时间。如果任何一层失败，先回到 `--arm 0` 或 mock，定位完再继续。

## 5. 手机视觉命令模板

### 试机和采样

```powershell
python code/camera/phone_fall_watch.py `
  --phone http://<手机IP>:8080 `
  --master http://<主脑地址>:8000 `
  --thresh 18 `
  --cooldown 30 `
  --arm 0
```

### 正式触发

```powershell
python code/camera/phone_fall_watch.py `
  --phone http://<手机IP>:8080 `
  --master http://<主脑地址>:8000 `
  --thresh <现场标定值> `
  --cooldown 30 `
  --arm 1 `
  --room 客厅 `
  --src phone_watch
```

`--arm 0` 是默认起点。没有完成三组采样、接口验证和下游准备前，不要直接使用 `--arm 1`。

## 6. 常见故障的定位顺序

| 现象 | 先查什么 | 处理方式 |
|---|---|---|
| `[NET] 手机串流不通` | 手机是否开流、IP 是否变化、是否同一热点 | 浏览器先开手机控制页；重新记录 IP；关闭省电限制 |
| `e` 长期为 0 | 取景是否冻结、`/shot.jpg` 是否真的更新 | 在镜头前挥手；重新取景；检查手机 App 的单帧接口 |
| 静止时频繁 `[FALL]` | 手机是否抖动、灯光是否闪烁、阈值是否过低 | 固定支架、避开直射光；阈值一次加 5 重新采样 |
| 模拟跌倒没有触发 | 倒地动作是否完整、画面是否覆盖地面、阈值是否过高 | 缓慢完整倒地并保持静止 3 秒；确认 `c_min > b_max` 后再调低阈值 |
| 视觉打印触发但主脑没反应 | 主脑地址/端口、`/mock/fall` HTTP 状态、主脑日志 | 先用同一 URL 手动 POST；确认主脑服务在运行；记录返回体 |
| 主脑返回 200 但机械手没动 | 主脑状态机、仓库 arm_service、硬件后端状态 | 交给主脑/硬件队友沿 `/status` 和历史记录排查；不要从手机脚本补发动作 |
| 机械手动作方向/幅度异常 | 寄存器、手号、速度和限位 | 立即停止真实动作；硬件队友回到寄存器资料和低风险单步测试 |
| X5 能启动但收不到手机 | X5 与手机是否同网、路由隔离、防火墙 | 用 X5 浏览器或 `curl` 先访问 `/shot.jpg`；必要时把手机和 X5 接到同一热点 |

## 9. 完成标准

### 视觉/手机部分完成

- 手机能稳定供帧，地址和网络记录完整；
- 静止、正常活动、模拟跌倒三组数据已记录；
- `--arm 0` 下误报可接受，模拟跌倒能稳定触发；
- `/mock/fall` 返回 200，主脑日志能看到来源；
- 连续三次完整演示的误报、漏报和时间均有记录。

### 真机硬件部分完成

- 手号、端口/总线、寄存器和电源已由硬件队友确认；
- 只运行仓库版本的 `arm_service.py`；
- 低风险单步姿态和 `/status` 读回通过；
- Panthera SDK（如使用）有真实动作映射和失败日志；
- 急停、断电和异常回退方式明确。

只完成前一组时，项目可以称为“视觉与主脑链路完成”；两组都完成并且三次端到端通过后，才可以称为“现场真机验收完成”。
